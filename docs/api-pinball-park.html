1. 通用约定

  • 传输：全站 HTTPS；所有写接口强制签名（见 §2）。
  • Base URL：https://api.pinball-park.com（小游戏与 App 共用；多副本无状态，状态在 MySQL/Redis）。
  • Content-Type：application/json; charset=utf-8，请求体为 JSON。
  • 时间格式：Unix 毫秒时间戳（timestamp 字段）。

1.1 公共请求头

Header必填说明
Authorization写接口必填Bearer {token}，登录后下发
X-Device-Id是设备唯一标识（小游戏 OT / App IDFA 脱敏）
X-Platform是wechat_mini / app_ios / app_android / h5
X-Nonce写接口必填单次随机串（≤36 字符），单次有效
X-Timestamp写接口必填毫秒时间戳，±5min 窗口
X-Sign写接口必填HMAC-SHA256 签名（§2）
X-Request-Id否客户端幂等/链路追踪用，原样返回

1.2 响应信封

所有接口统一返回：

{
  "code": 0,            // 0=成功；非0见错误码表
  "message": "ok",     // 人类可读描述；失败时为错误原因
  "data": { ... },      // 业务数据；失败时为 null
  "requestId": "r-xxxx" // 服务端追踪 ID
}

2. 签名与鉴权规范

防篡改 + 防重放双保险（对应架构 §14）。所有写接口必须带 X-Sign。

2.1 签名串构造

// 1) 取待签原文（拼接，无分隔符）
stringToSign = token + nonce + timestamp + canonicalBody

// 2) canonicalBody = JSON 序列化请求体，key 按字典序排序（稳定可复现）
// 3) 签名
X-Sign = HMAC-SHA256( deviceSecret, stringToSign ).toHexUpper()

// deviceSecret 由登录下发，存于客户端安全存储；可与 token 共用一套派生密钥

2.2 服务端校验顺序（Go 参考实现）

// 架构/后端均为 Go；以下为 Gin 中间件伪代码
func SignMiddleware(c *gin.Context) {
    token   := c.GetHeader("Authorization")[7:] // strip "Bearer "
    nonce   := c.GetHeader("X-Nonce")
    ts      := c.GetHeader("X-Timestamp")
    sign    := c.GetHeader("X-Sign")
    body    := rawBody(c) // 必须读取原始 body（不可经 JSON 反序列化再回写）

    // a. 时间窗口 ±5min
    if abs(nowMs()-parseInt64(ts)) > 5*60*1000 { abort(40104) }
    // b. nonce 单次有效（Redis SET NX，TTL 10min）
    if !redis.SetNX("nonce:"+nonce, 1, 10*time.Minute) { abort(40103) }
    // c. 重算并比对签名
    secret  := loadDeviceSecret(token)
    expect  := hmacSHA256(secret, token+nonce+ts+canonical(body))
    if !constantTimeEq(expect, sign) { abort(40102) }
    c.Next()
}
读取 rawBody 而非反序列化后的对象，避免序列化差异导致签名不一致；canonical 函数须与客户端约定一致（推荐 encoding/json + map[string]interface{} 排序后 marshal）。

3. 错误码表

codemessage含义 / 客户端处理
0ok成功
40001invalid_param参数缺失/越界（如 bet 不在 5–99）；提示并阻断
40101unauthorizedtoken 缺失/过期；走 refresh 或重新登录
40102sign_invalid签名校验失败；检查 deviceSecret/序列化
40103nonce_reusednonce 重复；客户端每次请求换新 nonce
40104timestamp_out_of_window时间戳越界；校准设备时间
40901balance_insufficient弹珠余额不足（open/bet/ad reward 前置校验）；引导领珠
40902round_conflictroundId 状态机冲突（重复 launch/settle 或状态不符）；以首次结果为准
40903game_locked该用户已有进行中的局（game_lock）；需先 settle
42901rate_limited广告场景达当日/单局频控上限；提示"今日已达上限"
42902ad_verify_failed广告平台 server verify 不通过；不发奖
50001server_error服务端内部错误；可重试（写接口需幂等）
幂等约定：所有「写价值」接口（open/bet/launch/settle/ad/callback）均由服务端以 roundId 或 thirdTransId 做行级锁 + 状态机去重，客户端可安全重试；重复请求返回首次结果，不产生二次扣减/发奖。

4. 鉴权模块（Auth）

POST/auth/login

登录/注册一体；跨端统一 uid；游客可兜底（下发临时 uid，绑定后可迁移资产）。

Request

{
  "platform": "wechat_mini",   // wechat_mini | app_ios | app_android | h5
  "code": "wx_login_code",     // 微信/平台登录 code（code 或 phone 二选一）
  "phone": "138xxxx",           // 手机号验证码登录（可选）
  "deviceId": "d-xxxx",
  "deviceFp": "fp-xxxx"          // 设备指纹（风控用）
}

Response

{
  "uid": "u_10001",
  "token": "eyJ...",
  "refreshToken": "rt-...",
  "expiresIn": 7200,            // token 秒数
  "isNewUser": false,
  "assets": { "beans": 30, "cards": 0, "points": 0 }
}
登录即送每日登录 30 珠（在 daily:{uid}:{date} 未签到时发放，幂等；open 不再发放）。deviceSecret 为设备级长期密钥，登录时随 token 一并安全下发，与 token 解耦——token 刷新（/auth/token/refresh）不影响 deviceSecret，写接口签名始终用同一 deviceSecret。
POST/auth/token/refresh 
Request:  { "refreshToken": "rt-..." }
Response: { "token": "eyJ...", "expiresIn": 7200 }

5. 游戏模块（Game）

一局分四段：open →（可选）bet → launch → settle。价值在 launch 一次定死，settle 才入账（架构 §9）。单用户同时仅一局进行中（game_lock:{uid}）。
POST/game/open ★ 锁投入·抽倍数/亮灯出口 
Request:  { "bet": 5 }                       // 5 ≤ bet ≤ 99，受余额约束
Response: {
  "roundId": "r-20260729-a1b2",
  "multiplier": 8,                    // 本局单倍数（×2/×4/×6/×8/×16/×32 加权）
  "litExits": [3, 5, 7, 9],            // 亮灯出口（可中区），子集 of 1..12
  "rtpApplied": 1.35,                  // 含新手保护系数（前5局1.5→递减）
  "balance": 25                        // 扣 bet 后余额
}

事务：校验余额 ≥ bet → 扣 bet 入 bean_ledger(type=open_lock) → 写 game_rounds(status=bet_locked) → 置 game_lock:{uid}。

POST/game/bet 加注（可选） 
Request:  { "roundId": "r-...", "addBet": 10 }   // effectiveBet ≤ 99
Response: { "effectiveBet": 15, "estReward": 120 }  // estReward = effectiveBet×multiplier（预估）

事务：校验余额 ≥ addBet 且 effective_bet+addBet ≤ 99 → 扣 addBet（行锁 UPDATE beans=beans-delta WHERE beans≥delta）→ 更新 effective_bet。与 launch 串行于同一 roundId 锁。

POST/game/launch ★ 服务端定命中/落点/奖励/卡 
Request:  { "roundId": "r-...", "chargePower": 72 }   // chargePower 0..100 仅演出用
Response: {
  "hit": true,
  "targetExitId": 7,              // 命中→litExits 内按权重选；未中→暗口集（litExits 之外的独立沉没通道，见 PRD 5.3）
  "rewardBeans": 120,            // effectiveBet×multiplier（未中=0）
  "cards": 3,                    // hit && rewardBeans≥40 → min(5, floor(R/40))；否则 0
  "multiplier": 8,
  "rtpApplied": 1.35
}
命中算法（服务端唯一权威）：P(hit) = rtpApplied / multiplier，用密码学安全随机源。命中从 litExits 按「低倍出口权重高、高倍稀有」抽取；未中从暗口集选。chargePower 仅记录、不参与判定。写入 game_rounds(status=launched)，不发放。
POST/game/settle ★ 入账（弹珠+卡） 
Request:  { "roundId": "r-..." }
Response: {
  "beans": 145,                   // 入账后弹珠余额（含 rewardBeans，翻倍则×2）
  "roundCards": 3,               // 本局获得积分卡
  "totalCards": 3,               // 入账后总积分卡余额
  "balance": 145,
  "doubled": false               // 是否看过视频翻倍
}

事务：幂等（同 round 仅一次）；若 hit 则 +rewardBeans 入 bean_ledger(type=settle_win)、+cards 入 point_ledger；写 status=settled；释放 game_lock:{uid}。响应返回 roundCards（本局获得）/ totalCards（总余额）。失败重连可经 /game/round 重查重放。

客户端「再来一局」必须等本局 settle 成功（释放锁）后再 open；正常并发 open 将收到 40903 game_locked。game_lock 设 TTL（如 30min）：超时未 settle 自动置 round.status=aborted 并释放锁、回滚 open 锁定的 bet（写 bean_ledger(type=open_refund)），防崩溃死锁。
GET/game/round/{roundId} 断线恢复 / 状态查询

客户端启动或断线重连时，若检测到存在未结算局（本地残留 roundId 或服务端返回 40903），调用本接口拉取服务端权威状态，据此消费演出与入账，不重开新局。

Response: {
  "roundId": "r-...",
  "status": "bet_locked|launched|settled|aborted",
  "hit": true,                     // launched/settled 时返回权威结果
  "targetExitId": 7,
  "rewardBeans": 120,
  "cards": 3,
  "doubled": false,
  "settleDone": true                // 是否已入账（true 则客户端直接展示结果，不重复 settle）
}
恢复策略：settled → 直接展示结果（幂等，无需再 settle）；launched → 客户端播放落点演出后调 settle；bet_locked 且未超时 → 续播拉杆演出后调 launch；bet_locked 且已超时/aborted → 资产已回滚，引导用户重新 open。所有路径均不丢资产、不重复发奖。

6. 广告模块（Ad）

发奖铁律：领珠 +88 / 翻倍奖励仅在 /ad/callback server verify 通过后由 AdModule 调 AssetModule 入账（架构 §11.2 / 铁律二）。客户端不可伪造"已看完"。
POST/ad/reward 频控前置校验 
Request:  { "scene": "claim_beans", "roundId": "r-..."? }  // scene: claim_beans(常驻领珠)|double(命中翻倍)|sign(每日签到看视频)|high_multiplier(高倍挑战入场)
Response: {
  "canWatch": true,
  "remainingTimes": 5,           // 本场景当日剩余次数
  "reason": null                   // canWatch=false 时返回 "daily_limit"（当日 6 次用尽）；领珠为常驻按钮，余额充足亦可点，无 balance_enough
}

领珠（claim_beans）为常驻按钮，任意余额可点（PRD 5.2/5.4）；当日 6 次达上限返回 canWatch=false, reason=daily_limit，客户端置灰 + 提示"今日已达上限，明天再来"。无 balance_enough 之类原因。

POST/ad/callback ★ server verify 后发奖 
Request:  {
  "platform": "wechat",
  "scene": "double",              // claim_beans | double | sign | high_multiplier
  "thirdTransId": "wx-txn-xxx",  // 平台下发交易号，唯一索引去重
  "roundId": "r-..."?,           // double 场景必填
  "verifySign": "..."            // 平台回调签名（服务端验真）
}
Response: {
  "rewardBeans": 88,            // claim_beans→+88；double→本局 rewardBeans×2（如原 120→240）
  "cards": 0,
  "balance": 265
}
集成形态说明：本接口为「发奖逻辑抽象入口」。真实微信流量主 / 穿山甲为 平台服务端 → 我方服务端 的 server-to-server 回调（架构 §11.2），由 AdModule 验真平台签名后内部调用同一入账逻辑；客户端仅负责播放广告并（可选）在收到平台成功信号后通知本接口触发补发。无论哪种形态，发奖一律以 server verify 通过为前提。
翻倍时序：命中后点"看视频 ×2"→ 播广告 → 平台回调本接口 → 将本局 rewardBeans×=2, doubled=true（幂等，仅限 hit 且未翻倍）。若翻倍回调发生在 settle 之后，补一次入账事务（同 roundId 幂等累加），客户端补播额外 N 颗（PRD 5.3 / 架构 §9.3）。客户端须以 callback 成功返回的最新 doubled/balance/rewardBeans 刷新结果区——settle 旧响应（doubled=false）仅作兜底，不可作为终态。

7. 配置模块（Config）

POST/config/get 
Request:  { "keys": ["rtp","multiplierPool","kTiers","adFreq","board"]? }
Response: {
  "rtp": 0.90,
  "multiplierPool": [              // 倍数加权池，均倍 5.03（低倍高权重、×32 稀有）
    {"m":2,"w":30},{"m":4,"w":22},{"m":6,"w":14},{"m":8,"w":9},{"m":16,"w":3},{"m":32,"w":1.5}
  ],
  "kTiers": [5,20,50,80,120],       // 兑换所需卡数 K（兑换模块后续版本用）
  "adFreq": { "claimBeans":6, "double":10, "sign":1, "highMultiplier":3, "dailyTotal":20 },
  "board": { "exits":12, "tiltDeg":30, "boxCap":60 } // 板面：出口数/倾斜/出珠盒子容量

客户端启动拉取动态配置（RTP、倍数池、K 分层、广告频控、板面参数）。服务端为唯一校验方，下发值可经运营后台（ConfigModule/Admin）热更，无需发版。

9. 数据字典与幂等说明

9.1 枚举

字段取值
round.statusbet_locked → launched → settled（失败可 aborted）
ad.sceneclaim_beans / double / sign / high_multiplier
bean_ledger.typeopen_lock / bet_add / settle_win / open_refund / ad_claim / ad_double
point_ledger.typesettle_card（入账）/ exchange_cost（兑换扣减，后续版本）
platformwechat_mini / app_ios / app_android / h5

9.2 幂等关键

  • open/bet：余额扣减走 UPDATE beans=beans-delta WHERE beans≥delta 原子条件 + 行锁，余额不足即拒绝（防超投）。
  • launch/settle：以 roundId + 行级锁 + 状态机去重，重复请求返回首次结果。
  • ad/callback：thirdTransId 唯一索引去重，重放/伪造不发奖。
  • 单局并发：game_lock:{uid} 保证同一时刻仅一局进行中。

10. 一致性与下游依赖

与上游文档一致：
  • 四段事务、命中算法 P(hit)=rtpApplied/multiplier、卡规则 R≥40→min(5,floor(R/40))：对齐数值设计 v1.2。
  • 落点还原服务端定（launch 定 targetExitId）、物理溢出演出、出珠盒子容量 60：对齐 PRD 4.6/4.7/5.3。
  • 常驻领珠按钮、无结算弹窗、翻倍走 ad/callback：对齐 PRD 5.2/5.4。
  • 后端语言 Go（Gin/GORM）、签名 HMAC、数据模型 ER：对齐架构 v1.0。
