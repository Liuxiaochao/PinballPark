1设计目标与原则

1.1 核心原则（继承自 PRD 两条铁律）

铁律一：所有价值判定在服务端。投珠开局、倍数与出口抽取、命中判定、奖励发放、积分入账全部由服务端决定并落库。客户端仅做物理演出（收到 targetExitId 后引导球落入目标出口）。
铁律二：激励视频发奖必须走服务端回调验证。广告平台 server verify 通过后才发奖，杜绝客户端伪造"已看完"。

1.2 架构原则

  • 多端同构、平台隔离：Cocos Creator 一套代码发小游戏/App/H5；广告、登录、支付等平台差异收敛到适配层，游戏逻辑层不感知平台。
  • 物理为表、结果可控：客户端物理引擎只负责真实手感演出；结果（命中、落点、奖励）服务端先定，引导力只是把球"扶"进已定出口。
  • 账本强一致、演出可重连：弹珠/积分入账以服务端为准、事务内完成；客户端演出失败/掉线，服务端结果仍可补发（结算幂等）。
  • 配置驱动、可灰度：RTP、倍数池、K 阈值、广告频控全部后台可配，支持按用户分群 A/B（如新手保护曲线）。
  • 演进优先：服务端先单体分模块（NestJS modules），量大再拆微服务；接口与存储设计预留迁移路径。

2总体架构

自顶向下分五层：客户端 → API 网关/接入层 → 后端应用（NestJS 模块）→ 存储（MySQL/Redis）→ 第三方（广告/兑奖/统计）。两条铁律的约束力体现在"价值判定"全部收敛在后端应用层，客户端不持有任何产生价值的随机源。

多端与接入层：微信小游戏与 App 共用同一后端，但走独立接入域名/证书；广告回调由广告平台主动推送到服务端（不依赖客户端回传），天然防伪造。H5 仅作分享传播，价值链路同构。

4物理仿真子系统（落点还原 + 30° 倾斜）

本子系统是"物理为表、结果可控"的技术核心，需同时满足 4.6（两阶段仿真、结果受控、物理一致） 与 4.7（板面 30° 倾斜）。设计目标是：物理在板面局部坐标跑，渲染整体旋转 30°，使引导力退化为局部 X 轴修正。

4.1 坐标系与重力

  • 物理世界（局部坐标）：板面轴对齐；重力 g_local = (0, -g)；钉阵、通道墙、出口、出珠盒子均在轴对齐局部坐标定义（易于编排与离线验证）。
  • 渲染层：对"板面 + 球"整体施加 30° Z 轴旋转矩阵显示。局部竖直下落 → 视觉沿倾斜板"下坡"滚动，与真实倾斜板受重力分量漂移观感一致（4.7 已确认）。
  • 漂移方向：默认顺时针 30°（视觉向右下漂）；纯渲染参数，物理侧不改重力向量，美术阶段可微调旋转角。

4.2 两阶段仿真（对应 4.6）

  • 阶段① 自由碰撞区：弹簧杆发射 + 钉板钉阵真实 Box2D 弹跳（含"+30° 渲染"观感）。此段结果不可预测，提供手感与参与感（4.6 阶段①）。
  • 阶段② 引导路由区：球过"路由控制线"后，下方通道由真实静态墙体构成（碰撞真实）；在通道入口施加有界横向引导力（= 局部 X 修正），把球送入服务端指定的 targetExitId 通道。引导幅度限制在"自然弹跳方差包络"内，观察者无法区分于真实混沌（4.6 物理一致性结论）。
  • 暗口通道：未命中时 targetExitId 指向暗口（沉没通道），与出珠盒子几何隔离（呼应 5.3 暗口设计），避免"掉珠却没奖"的困惑。

4.3 引导力控制器（GuideForceController）

  • 输入：targetExitId（局部坐标 x 目标）、球当前位置。
  • 每物理步施加朝向目标 x 的力，幅度随距目标距离衰减（PD 控制器）；当球进入目标通道开口后撤力，由真实墙体接管。
  • 禁用项：瞬移、直接 setPosition、反物理加速、穿透墙体——违反 4.6 物理一致性。所有位移均经由对真实几何的碰撞。
  • 备选（4.6 备选方案）：若改用"发射参数偏置法"，此处改为离线求解器查表，引导力设为 0；首发实现有界引导即可。
性能边界：自由碰撞区钉数控制在移动端可实时仿真范围（建议钉阵 ≤ 60 钉、子步频 ≥ 60Hz）；路由区墙体为静态，开销极低。物理步与渲染分离（fixed timestep）。

5落点还原：客户端实现要点

客户端在 AWAIT_LAUNCH 收到服务端返回的 targetExitId 与"是否命中"后开始物理演出。关键工程点：

  • 时序：开局仅下发倍数 + 亮灯出口（供展示）；targetExitId 必须在拉杆请求返回拿到，仿真开始前施加引导力（4.6 时序配合已确认）。
  • 拉杆力度仅演出：蓄力值（0~1）影响发射初速区间抖动，不传参与结果；服务端结果在拉杆请求时已定，故"蓄力大就更容易中"是错觉，符合"运气游戏"定位（4.6 拉杆边界）。
  • 取消：蓄力中取消（手指移出命中区/进取消区松手）→ 不发起拉杆请求、不扣珠、回到 BET_SET（PRD 5.3 拉杆操作）。
  • 落定检测：球进入目标通道并低于控制线即判"落定"，触发结算演出（无弹窗，结果直显 5.3）。
  • 断线重连：若 SIMULATING 中掉线，重连后向服务端查询本局状态；服务端返回权威结果，客户端据结果"快进"到对应演出帧或补发入账（账本幂等，见 §10）。
反外挂要点：因为落点由服务端定、客户端改不了 targetExitId，任何"物理外挂/自动瞄准"都只改变演出观感、拿不到更多奖励——这是服务端定结果的天然反作弊红利（呼应 PRD 9.2）。

6出珠盒子区域与物理溢出（实现 5.3）

命中后奖励珠 N = 有效投入 × 倍数 以"逐颗掉落入出珠盒子"演出；超过容量上限 60 的部分由物理引擎驱动溢出滚落（5.3 已确认）。实现约束：

6.1 出珠盒子几何

  • 盒子为板面底部的静态刚体围栏（左/右/底墙），位于局部坐标，随板面 30° 渲染。
  • 容量上限 CAP = 60（纯显示参数，数值文档 §6）。落入盒子的珠为真实动态刚体，碰撞盒壁、可在盒内堆叠。

6.2 溢出物理实现

  • 盒子满（计数 ≥ 60）后继续生成的珠，从盒沿溢出为真实 Box2D 刚体，沿盒壁滚落消散（非脚本补间，5.3 溢出物理驱动已确认）。溢出珠与盒内珠同处一个物理世界。
  • 权威计数与物理珠解耦：HUD 显示的奖励数 = 服务端下发的 N（权威）；物理珠只负责"视觉掉落实感"。即使溢出珠滚落消失，入账以 N 为准，盒子永不丢失应得奖励。

6.3 性能约束（关键）

N 可能高达 1980（99×20），禁止生成 N 个物理刚体。实现策略：
  • 对象池：盒内至多存活 CAP(60) 颗 + 溢出若干（建议 ≤ 20）真实珠；超出部分以"代表珠 + 数字滚动"替代演出。
  • 下落节奏分级：N 小则单颗快落；N 大则连续喷落并加速，且超过视觉上限后直接以数字累加收尾，避免长演出拖时长。
  • 看视频翻倍：命中后点 ×2，N→2N，补播额外 N 颗（同样走 CAP 与溢出逻辑），数字累加至 2N。

6.4 暗口通道（未命中）

  • 未命中球进入与盒子隔离的沉没通道（另一组静态围栏），落底后消散；结果区显示"本局投入 X 颗已沉没"。亮灯出口与暗口几何分属不同通道，杜绝误读。

  • 登录后持有服务端下发的 token（Redis 会话）；所有写接口带 token + nonce + timestamp + sign。
  • sign = HMAC(deviceSecret, token+nonce+timestamp+body)，防篡改与重放（§14）。

8服务端架构（NestJS 模块）

后端以 NestJS 单体起步，按业务域分 module；价值判定与账本集中在 Game/Asset 模块，保证铁律一。模块间通过服务调用，不跨库直连。

9核心判定：落点还原服务端实现（重点）

这是 4.6 的落地。一局分四次调用，价值在 launch 一次定死，settle 仅入账。

9.1 四次调用与事务边界

// ① open：锁定初始投入
POST /game/open  { bet }  → { roundId, multiplier, litExits[], rtpApplied }
  // 事务：校验余额≥bet；扣 bet 入 bean_ledger(锁定)；写 game_rounds(status=bet_locked)

// ② bet（加注，可选）：追加锁定（PRD 4.4）
POST /game/bet   { roundId, addBet }  → { effectiveBet, estReward }
  // 事务：校验余额≥addBet 且 effectiveBet≤99；扣 addBet；更新 effective_bet

// ③ launch：服务端定结果（铁律一核心）
POST /game/launch { roundId, chargePower }  → { hit, targetExitId, rewardBeans, cards }
  // 事务：幂等(同round仅一次)；取本局multiplier/litExits
  //   P(hit)=rtpApplied / multiplier ；用安全随机源(含盈亏池/新手曲线)
  //   命中→从litExits按权重选targetExitId；rewardBeans=effectiveBet*multiplier
  //   未中→从暗口集选targetExitId；rewardBeans=0
  //   cards = hit && rewardBeans≥40 ? min(5, floor(rewardBeans/40)) : 0
  //   写game_rounds(status=launched, hit,targetExitId,rewardBeans,cards)；不发放
  //   chargePower 仅记录(演出用)，不参与任何判定

// ④ settle：演出结束入账
POST /game/settle { roundId }  → { beans, cards, balance }
  // 事务：幂等(同round仅一次)；若hit则+rewardBeans入账、+cards入积分账本
  //   写 status=settled；返回最新余额。失败重连可重查重放。

9.2 命中判定算法（RTP 反解）

  • 单局期望返还率恒定：P(hit) = rtpApplied / multiplier。无论倍数多大，单局期望返还 = 投入 × rtpApplied（数值文档 §2）。
  • rtpApplied 取：基础 RTP 0.90 × 新手保护系数（前 5 局 1.50→线性递减→第 16 局 0.90）× 盈亏池修正（个体/全局池防止极端偏差）。
  • 安全随机源：服务端用密码学安全随机（如 crypto.randomBytes 派生的 [0,1)），不依赖客户端或时间可被预测的种子。
  • 亮灯出口权重：命中时 targetExitId 在亮灯出口集合内按低倍→高倍出口权重递减抽取（高倍出口稀有，对应 4.3 12 出口方案）。

9.3 翻倍（看视频 ×2）

  • 命中后点"看视频 ×2" → 播广告 → 平台回调 /ad/callback 验真 → 内部将本局 rewardBeans ×= 2、doubled=true（仅限 hit 且未翻倍过，幂等）。
  • 客户端补播额外 N 颗（§6.3）；settle 时入翻倍后的值。若翻倍在 settle 之后才回调，则补一次入账事务（同 roundId 幂等累加）。
为什么奖励不在 launch 直接入账？ 若 launch 即入账、客户端演出崩溃，账面已加但玩家没看到——体验与对账皆乱。改为 launch 只"定结果"、settle 才"入账"，服务端全程掌握权威状态，客户端仅消费演出。断线可重连补发，账本零误差。

10资产账本与并发安全

10.1 账本模型（强一致）

  • 弹珠账本 bean_ledger：每笔变动 Append-Only，含 type(open_lock/bet_add/settle_win)、delta、balance_after、ref_round。
  • 积分账本 point_ledger：积分卡入账（settle）/ 兑换扣减（exchange）。不可逆流（珠→积分单向，PRD 4.5）。
  • 余额 = 账本末态余额，不另存易失字段；关键读走事务或 Redis 缓存（带失效）。

10.2 并发与幂等

风险对策
同一局重复 launch/settlegame_rounds 行级锁 + 状态机；重复请求返回首次结果（幂等）
并发开局超投（余额为负）open/bet 扣减走 UPDATE ... SET beans=beans-delta WHERE beans≥delta 原子条件 + 行锁；不足则拒绝
加注与拉杆竞态bet 与 launch 串行化于同一 roundId 锁；launch 以"已锁定 effectiveBet"为准，不接受客户端传参覆盖
广告回调重放/伪造thirdTransId 唯一索引去重 + server verify（铁律二）
兑换并发扣卡事务 + 订单状态机（created→…→done/failed），失败补偿退卡
单用户同一时刻仅允许一局进行中（Redis game_lock:{uid}），从协议层面杜绝"一局没结算又开下一局"的并发扣减漏洞。

11兑换 / 广告 / 风控（服务端）

11.1 兑换（ExchangeModule）

  • 下单流程：风控校验（实名/设备/限额/黑名单）→ 扣积分卡（事务）→ 调第三方兑奖平台 API → 写订单 → 履约回调更新状态。
  • 订单状态机：created → risk_checked → deducted → fulfilling → done / failed(退卡)（PRD 7.2）。失败补偿必须幂等（第三方回调可能多次）。
  • 兑换所需卡数 K 分层（5/20/50/80/120）由 ConfigModule 下发，服务端为唯一校验方（铁律一：价值判定在服务端）。

11.2 广告（AdModule）

  • 场景频控：领珠每日 6 次、翻倍每局 1/每日 10、签到 1、高倍 3、单日总 20（PRD 6.1/6.2），Redis 每日计数 + 过期。
  • 发奖：领珠 +88（或翻倍奖励）仅在 /ad/callback server verify 通过后由 AdModule 调 AssetModule 入账。

11.3 风控（RiskModule）

  • 设备指纹（小游戏 OT/App IDFA 脱敏）+ 账号行为画像；同设备多账号、异常兑换频率进黑名单/人工队列。
  • 经济闸门（PRD 6.5）：实时算 人均观看×eCPM ÷ 人均积分成本，低于 1.2 自动/人工收紧（降 RTP / 升 K）。

14安全与风控技术实现

  • 传输与鉴权：全站 HTTPS；token 短期有效 + refresh；敏感写接口需 sign。
  • 防重放：nonce 单次有效（Redis 短 TTL 去重）+ timestamp 窗口校验（±5min）。
  • 防篡改：sign = HMAC(deviceSecret, token+nonce+timestamp+body)，服务端重算比对。
  • 防外挂：结果服务端定（§9），客户端改 local 文件/内存无效；引导力不可被客户端改写 targetExitId。
  • 防刷：广告 thirdTransId 唯一索引；同设备多账号识别；兑换前实名/手机号校验。
  • 审计：所有账本/订单 Append-Only，可追溯；运营后台可查任意 uid 全流水。

15部署拓扑

  • 后端：NestJS 容器化（Docker）+ K8s/轻量云；多副本无状态，状态在 MySQL/Redis。小游戏与 App 接入层独立 Ingress/域名，共用后端服务。
  • 存储：MySQL 主从（读写分离，账本强一致走主库）；Redis 哨兵/集群（会话/限流/日计数）。
  • 第三方：广告回调接收端需公网可达且验签；兑奖平台 API 走内网/专线或加签 HTTPS。
  • 客户端构建：Cocos Creator 一处构建多 target（微信小游戏包 / App 原生工程 / H5），CI 出包。

18风险与技术债

  • 引导力穿帮风险：引导幅度若超自然方差包络，老玩家可能察觉"球被吸走"。对策：离线标定引导力上限 + QA 抽样回放；备选发射参数偏置法（§4.3）。
  • 物理溢出演出成本：极端 N（1980）需对象池与节奏分级兜底，否则低端机掉帧（§6.3）。
  • RTP 配置错误：误配 RTP/K 可能瞬间击穿经济模型。对策：配置变更审批 + 经济闸门自动熔断（§11.3）。
  • 跨端账号：小游戏 openid 与 App 手机号需 union_id/手机号绑定打通，二期重点（PRD 12 M5）。
  • 技术债：单体起步，Game/Asset 若膨胀再拆微服务；引导力算法、物理参数需 M1 原型实测调参。
