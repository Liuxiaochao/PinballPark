0项目概览与已确认决策

参考实体游戏机"弹珠乐园"的核心体验：投珠开局 → 随机倍数与亮灯出口 → 拉杆弹射 → 钉板碰撞 → 落入出口结算奖励珠 → 累积积分兑换实物。线上化后以广告变现替代投币收入。

1总体架构 已确认

1.1 分层结构

  • 客户端（Cocos Creator 3.x，一套代码）：微信小游戏（微信登录 + 微信流量主广告）、iOS/Android App（手机号登录 + 穿山甲/聚合广告）、H5（分享传播）。广告 SDK 按端隔离封装，游戏逻辑层不感知具体广告平台。
  • 后端（Node.js / NestJS 单体分模块）：账号服务（跨端统一账号）、游戏结果服务（RTP 判定 · 倍数出口抽取）、资产账本服务（弹珠 · 积分流水）、兑换服务（商城 · 订单履约）、广告回调服务（服务端验证发奖）、风控服务（防刷 · 限额 · 黑名单）、运营后台（数值配置 · 数据看板）。
  • 存储：MySQL（账本、订单、流水），Redis（会话、限流、每日计数）。
  • 第三方：广告平台（微信流量主、穿山甲）、第三方兑奖平台、数据埋点统计。

1.2 两条铁律

铁律一：所有价值判定在服务端。投珠开局、倍数与出口抽取、命中判定、奖励发放、积分入账全部由服务端决定并落库；客户端仅做物理演出（收到结果后引导弹珠落入目标出口）。
铁律二：激励视频发奖必须走服务端回调验证（微信 / 穿山甲均支持 server verify），杜绝客户端伪造"已看完广告"。

2.2 倍数与出口设计（12 出口方案）

倍数档亮灯出口数 / 12直观难度说明
×25–6 个低保底体验档，高频出现

每局开始由服务端从倍数池加权抽取当局倍数并确定亮灯出口集合；未命中亮灯出口则本局投入弹珠沉没。

2.3 RTP（返奖率）模型

  • 目标综合 RTP：85%–95%，运营后台可配；数值以"广告收益 ≥ 奖励成本 × 安全系数"为约束反推。
  • 新手保护期：新用户前 N 局提高 RTP（先赢体验），随后回归常态曲线（参考实体机"先赢后输"，但避免过度诱导，需配合合规提示）。
  • 服务端按玩家个人盈亏池 + 全局池双重控制，防止个体极端偏差。

2.5 积分产出（参考实体机积分卡规则）

  • 单局命中奖励珠 ≥ 30 颗 → 1 张积分卡；≥ 60 颗 → 2 张；以此类推，每局上限 5 张。
  • 1 张积分卡 = 固定积分值（如 10 分），积分只增不减（兑换时扣除）。
  • 弹珠是"游戏内循环资源"，积分是"兑换资产"，两者单向转换、不可逆流。

体验原则：广告全部为"玩家主动选择换收益"，无强制插屏打断核心操作；发奖统一走服务端 server verify 回调；单用户单日激励视频总次数封顶（初始 20 次）。
经济模型闸门：运营后台实时监控 人均广告观看次数 × eCPM ÷ 人均积分产出成本，比率低于安全阈值时自动收紧积分产出（降低 RTP / 积分卡门槛上调），保证不亏损。

4.3 关键规则

  • 兑换限额：单用户每日 / 每月兑换上限；高价值商品需累计活跃天数门槛。
  • 订单状态机：created → risk_checked → deducted → fulfilling → done / failed(退积分)，全流程流水可审计。
  • 实物兑换需收货信息；虚拟券直充手机号 / 账号。

5合规与风控要点 待确认

合规红线：① 弹珠不可用现金购买，切断"花钱 → 随机 → 实物"的博彩链路；② 积分与奖品不可逆向兑换成现金；③ 概率公示（倍数档位与出现概率在游戏内可查）；④ 未成年人防沉迷与消费提示；⑤ 遵守微信小游戏平台关于抽奖类玩法与实物发放的审核规范。
  • 防刷：设备指纹 + 账号行为画像；广告回调去重；同 IP / 同设备多账号限制。
  • 防外挂：结果服务端判定使物理外挂无效；接口签名 + 时间戳防重放。
  • 羊毛党：兑换前实名 / 手机号校验，异常账号进入人工审核队列。

  • 核心指标：DAU / 次留 / 7 留、人均局数、人均激励视频次数、eCPM、ARPU（广告）、积分产出成本、兑换率、LTV/CAC。
