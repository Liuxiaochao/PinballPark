2. P0 — 阻塞问题（必须闭环后才能定稿）

P0-1 经济生命线仿真与每日广告频控不自洽（致命）

证据：实跑 economy_sim.py 实际输出 重度视频 52.3 次/日、轻度 12.4 次/日；而 PRD §6.2 与 API adFreq.dailyTotal=20 规定单用户单日激励视频总次数封顶 20 次。仿真据此算出重度广告收益 ¥15.68/日（=52.3×eCPM 0.3），直接相关于"K=80 重度 A/C=1.25×"的结论。

影响：将频控 20 次/日作为硬约束代入，重度广告收益将降至约 20×0.3=¥6（≈原值的 38%），每卡收益比值由 0.086 跌至约 0.033，K=80 可持续单价由 ¥6.88 跌至约 ¥2.6，对 ¥5 基准比值由 1.38× 跌至约 0.53×——生命线直接破防。文档声称"v1.2 仿真验证满足生命线"在真实产品约束下不成立。

建议：① 在 simulate_day 中增加 dailyVideoCap=20 硬约束（领珠/翻倍/签到/高倍共享额度），并据余额与频控重算可玩局数与发卡；② 重跑后若 A/C 仍 ≥1.2×，则在文档显式注明"已在 20 次/日频控下验证"；③ 若破防，须重新调参（上调 eCPM 假设、下调 RTP、上调 K、或放宽频控），调参后禁止只改表格，必须重跑脚本回填（呼应数值文档自身 NUM-09 纪律）。

P0-2 仿真 K 扫描范围与文档推荐阶梯不匹配（生命线结论无实证）

证据：脚本第 109 行 for K in [3, 5, 8, 10, 15, 20, 30, 50]，最高仅 K=50，从未运行 K=80（实物主档）/K=120（高实物档）。而数值文档 §3.2 表格与 §4.1 却给出 K=80（重度 ¥6.88、比值 1.38×）、K=120（¥10.31）的数值，并标注"数值来自 docs/sim/economy_sim.py"。

影响：主档/高档的生命线比值（1.25×/1.38×）是手工按公式 K×(广告收益/卡数) 外推，脚本从未产出，文档"数值来自脚本"的声明与事实不符；K=80/120 的可持续性缺乏可复现证据。

建议：将脚本 K 循环改为 [5,20,50,80,120]（对齐 PRD §7.1 / 数值 §3.2 阶梯）并重跑，使 §3.2/§4.1 表格可由脚本直接产出；或如实标注 K=80/120 为"公式外推、待脚本覆盖"。

P0-3 板面 30° 倾斜模型：PRD 与架构/UI-UX/测试 直接冲突

证据：PRD §4.7 明确定义"板面相对屏幕绕 Z 轴旋转 30°（屏幕平面内的 2D 旋转，非 3D 透视变形），即呈 30° 平行四边形，物理在板面局部坐标跑、渲染整体 2D 旋转"。而架构 §4.1 与测试 §6 UI-01 采用"perspective + rotateX(30°)（机台后仰，3D 透视，板面有纵深）"。

影响：这是两套根本不同的实现——2D 平面旋转 vs 3D 透视后仰。物理重力方向、引导力坐标系、渲染层、测试验收标准（UI-01 "板面有纵深" vs PRD "非 3D 透视"）全部随之不同。架构 §4.1 还称 3D 后仰"替代旧方案'竖直板+纯视觉旋转'"，与 PRD 当前方案相悖。不裁决将导致 M1 物理原型实现分歧。

建议：由架构/客户端负责人裁决统一为单一模型（推荐 3D 后仰 rotateX，更贴近实体机"机台后仰、球受重力分量沿板下滑"的真实物理与观感），并同步修订 PRD §4.7 措辞与测试 UI-01，使三者一致。评审记录：当前 PRD §4.7 自述"绕 Z 轴 2D 旋转"与同节"视觉沿倾斜板下坡滚动"在 2D 旋转下缺乏真实重力分量，物理自洽性弱于 3D 方案。

P0-4 Exchange（商城兑换）首发范围：PRD 标 P0 与其余文档"后续版本"矛盾

证据：PRD §3 功能清单将 #5 积分系统、#7 商城与兑换均标 P0 首发必备，§7 详述兑换订单状态机；但 API §8 明确"本版不实现 Exchange"、架构 §13 标"后续版本"、测试 §9 #6 标"延后"、运营 §9 将 Exchange 履约列入"短期（首发后）"。

影响：首发是否包含实物兑换未对齐，将导致排期、API 工作量、测试范围与合规准备（微信实物发放审核）整体偏差。

建议：二选一明确：① 若首发含兑换——API 须补全 Exchange 接口契约、测试须补 §9 #6 用例；② 若首发仅做"积分/卡积累 + 虚拟档"，将 PRD §3 的 #5/#7 降级为 P2 并注明"实物兑换后续版本"，与 API/架构/测试/运营一致。推荐②（与多数文档一致），但需在 PRD 内保持一致。

3. P1 — 重要问题（定稿前应修正）

P1-5 运营 §4 杠杆表 "eCPM 走弱时降 K" 方向写反

运营 §4 写"eCPM 走弱时优先降 K，不抬 40 门槛"；但数值 §8、数值 §4、架构 §11.3 均要求 eCPM 走弱时升 K（如 80→100）以收紧兑换。降 K 会让兑换更易、成本更高，与保生命线方向相反，若运营据此操作将加速击穿。建议改为"升 K / 提 K"。

P1-6 新手保护期（前 15 局 RTP 1.5→0.9）未纳入仿真

数值 §7 定义了新手保护曲线，架构 §9.2 / PRD §4.5 一致引用；但脚本 simulate_day 固定 rtp=0.90，未实现前 15 局高 RTP。首发前若干天的实际发卡量将高于稳态仿真值，初期 A/C 可能低于 1.2×，与"获客成本另行计量"的假设需对齐。建议仿真补充新手期建模或在文档显式标注"仿真为稳态、首发初期成本更高"。

P1-7 测试 NUM-09 数据错误

测试 §3.2 NUM-09 写"K=80 时重度 A/C=1.38×、轻度 1.38×"。实际（对 ¥5 基准）重度 1.38、轻度约 1.52；若按文档 §4.1 实际 ¥5.5 档则为重度 1.25×/轻度 1.38×。将重度值误复制给轻度，需校正。

P1-8 概率公示合规不充分

合规红线（PRD §9.1 / CMP-01）仅要求公示"6 档倍率及各自抽取概率（权重）"。抽奖类玩法通常还需公示综合返奖率 RTP 与命中概率。当前公示未覆盖 RTP，存在平台审核与监管风险。建议游戏内概率公示补充 RTP 及各档命中率，并在合规章节说明依据（微信小游戏抽奖类审核规范）。

P1-9 deviceSecret 长期设备密钥无轮换/吊销机制

API §4 将 deviceSecret 设为设备级长期密钥，参与所有写接口 HMAC 签名；测试 SEC-09 仅标 P2。一旦泄露可伪造任意请求签名。建议提升至 P1：补充密钥轮换、设备绑定、异常吊销，并明确泄露后的应急响应。

P1-10 术语不统一：弹珠 / 珠子

PRD / API / 架构统一用"弹珠"（beans）；数值文档与仿真脚本用"珠子"。建议全局统一为"弹珠"，脚本内部加注释对齐，避免实现期歧义。

P1-11 settle 响应终态歧义

API §5 警告"settle 旧响应中的 doubled 不可作为终态"，但响应未提供显式 double_pending 标志，客户端只能自行猜测是否待补发。建议在 settle 响应中增加 double_pending: bool，消除歧义。

P1-12 架构 §8 接口表含不存在的 double

架构 §8 将 double 列入 game 包对外接口，但 API 无此接口（翻倍通过 /ad/callback 实现，见架构 §9.3）。建议架构 §8 删除 double 或注明"非独立对外接口，由广告回调内部处理"。
